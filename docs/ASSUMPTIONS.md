# Assumptions

## General
1. This is a single-tenant API — there is no user authentication or authorization layer. The API is open for testing/demo purposes.
2. All monetary values are stored as `NUMERIC(15, 2)` in PostgreSQL, supporting up to 15 digits with 2 decimal places. This avoids floating-point precision issues.
3. The API accepts and returns amounts as numbers (not strings). Precision is maintained at the database level.

## Accounts
4. Account names do not need to be unique — multiple accounts can share the same name.
5. Accounts cannot be deleted or deactivated through the API.
6. The initial balance is always 0 and is enforced server-side. Any `balance` field in the create request body is ignored.

## Transactions
7. The `description` field is optional. If not provided, it is stored as `null`.
8. The `reference_id` uniqueness constraint is scoped to each account. The same `reference_id` can exist across different accounts, as stated in the requirements.
9. A duplicate transaction (same `account_id` + `reference_id`) returns HTTP 409 with the existing transaction's ID, rather than silently succeeding.
10. Transactions are immutable — there are no PUT, PATCH, or DELETE endpoints for transactions.
11. Negative balances are not allowed. A debit that would result in a negative balance is rejected with HTTP 422.

## Transfers
12. Transfers are implemented as two linked transactions: a debit on the source account and a credit on the destination. Both share a common `reference_id` pattern (`transfer-out-{ref}` and `transfer-in-{ref}`).
13. Transfers are atomic — if any part fails, the entire operation is rolled back.
14. Accounts are locked in a consistent order (by UUID) during transfers to prevent deadlocks.
15. A transfer to the same account is rejected.

## Data Integrity
16. All balance-modifying operations (transactions and transfers) use PostgreSQL transactions (`BEGIN`/`COMMIT`/`ROLLBACK`) with row-level locking (`SELECT ... FOR UPDATE`) to ensure atomicity and prevent race conditions.
17. The `balance` field on the `accounts` table is updated synchronously within the same database transaction as the transaction insert — it is not computed on-the-fly from summing transactions.

## Pagination
18. Default pagination: page 1, limit 10.
19. Maximum limit per page is 100 to prevent excessive queries.
20. Transaction history is always sorted by `created_at` in descending order (latest first).

## Technical
21. UUIDs (v4) are used for all IDs, generated by PostgreSQL's `uuid_generate_v4()`.
22. The API expects the `DATABASE_URL` environment variable to contain a valid PostgreSQL connection string (provided by Supabase).
23. The migration script is idempotent — it uses `CREATE TABLE IF NOT EXISTS` and `CREATE INDEX IF NOT EXISTS`, so it can be run multiple times safely.
24. CORS is enabled for all origins to support frontend development and testing.
